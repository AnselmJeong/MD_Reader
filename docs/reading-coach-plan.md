# Proactive 독서 코치 계획서

작성일: 2026-11-19 (같은 날 2차 개정) · 기준 버전: 0.9.0 (`27eec12`) · 상태: 제안 (코드 변경 없음) · 적용 범위: EPUB

## 1. 한 줄 결론

구현할 수 있고, LLM을 과하게 쓰지 않고도 할 수 있다. 핵심은 **"독자가 읽는 순간마다 LLM을 부르는 코치"가 아니라 "장(chapter)마다 한 번 미리 카드 묶음을 만들어 두고, 누구에게 무엇을 보여줄지는 LLM 없이 로컬에서 고르는 코치"** 로 설계하는 것이다.

- 장 하나당 백그라운드 LLM 호출 1회로 "카드 덱"(용어, 배경, 논증 구조, 반론, 연결 등 30~40장)을 만들어 SQLite에 영구 캐시한다.
- 화면에 어떤 카드를 드러낼지는 사용자 수준 모델이 로컬에서 결정한다. 여기에는 LLM이 전혀 들지 않는다.
- 사용자가 카드를 열고 "더 자세히"를 누를 때만 지금의 질문 창과 같은 본격 호출이 일어난다. 즉 비싼 호출은 항상 사용자의 명시적 수락 뒤에 온다.
- 책을 읽기 시작할 때 "어떤 코칭을 원하는지"를 먼저 묻는다. 건너뛸 수 있고 언제든 바꿀 수 있다. 이 답이 출발점이 된다.
- 그 뒤로는 수락과 거절 이력으로 수준과 취향을 다듬되, 거절의 이유("이미 알아요"와 "이런 종류는 관심 없어요")를 구분해서 받는다.
- 호버 카드는 Wikipedia 미리보기처럼 그림과 짧은 글을 함께 보여 주고, 원하면 그 내용을 기존 주석 기능으로 EPUB 안에 넣는다.
- 1차 적용 대상은 EPUB뿐이다. Markdown과 Quarto는 이 계획의 범위 밖이다.

## 2. 상상: 어떤 경험인가

같은 책, 같은 문단을 두 사람이 읽는다고 하자.

**초심자.** 책을 처음 열 때 "제대로 공부하기"와 "처음이에요", "먼저 제안하기"를 골랐다. 장을 열면 상단에 세 줄짜리 "이 장을 읽기 전에"가 접힌 채로 놓여 있다. 본문에는 페이지당 서너 군데에 옅은 점선 밑줄이 있다. "축의 시대"에 마우스를 올리면 Wikipedia 미리보기처럼 그림 한 장과 두 문장짜리 설명이 즉시 뜬다. 즉시 뜨는 이유는 이미 만들어 둔 카드이기 때문이다. 한 문단에서 유난히 오래 머물면 여백에 작은 칩이 조용히 나타난다. "이 문단, 풀어서 설명해 드릴까요?" 누르면 그때 비로소 AI가 답을 쓴다. 장이 끝나면 "핵심 세 가지와 스스로 확인해 볼 질문 두 개"가 기다린다.

**전문가.** 같은 책을 열며 "따져 가며 읽기"와 "익숙해요"를 골랐다. 같은 문단에서 "축의 시대" 밑줄은 보이지 않는다. 기초 용어 카드는 수준 필터에서 걸러졌기 때문이다. 대신 여백에 다른 종류의 칩이 있다. "이 주장에 대한 대표적 반론", "지난달 읽은 다른 책의 3장과 맞닿는 지점". 전문가에게 코치는 설명해 주는 사람이 아니라 옆에서 토를 달아 주는 동료다.

중요한 점은 수준에 따라 **양만 달라지는 것이 아니라 카드의 종류가 달라진다**는 것이다. 그래서 카드에 "난이도"와 "종류" 두 축을 모두 붙인다.

### 코치의 네 가지 역할 (카드 종류)

| 역할 | 카드 종류 | 주로 누구에게 |
|---|---|---|
| 해설자 | 용어 정의, 인물, 역사적 배경, 수식 풀이 | 초심자 |
| 길잡이 | 논증 구조("여기서 저자는 A를 전제로 B를 주장"), 앞 장과의 연결 | 초심자~중급 |
| 반론자 | 비판, 대안 해석, 이후 연구에서 뒤집힌 점 | 중급~전문가 |
| 연결자 | 다른 분야, 다른 책, 내가 남긴 메모와의 연결 | 전문가, 다각적 독서를 원하는 독자 |

### 코치가 나타나는 다섯 자리

1. **본문 밑줄 + 호버 카드.** Wikipedia식. 특정 단어나 구절에 붙는 카드. 그림이 있으면 함께 보여 준다.
2. **여백 칩.** 특정 단어가 아니라 문단 전체에 붙는 카드(논증 구조, 반론, 연결).
3. **장 앞 브리핑, 절 앞 요약, 장 뒤 정리.** 미리 알면 좋은 것, 절마다의 미리보기 요약, 읽고 난 뒤 확인 질문.
4. **막힘 감지 제안.** 한 문단에 오래 머물거나 되돌아갈 때 뜨는 "풀어 드릴까요?".
5. **코치 탭.** 채팅 패널 안에 이 장의 카드 전체 목록. 걸러져서 안 보이는 카드도 여기서는 볼 수 있다.

## 3. 현재 코드가 이미 제공하는 것

검토 결과, 필요한 부품의 절반 이상이 이미 있다.

| 필요한 것 | 이미 있는 것 | 위치 |
|---|---|---|
| 호버 카드 UI | 링크와 인용에 대한 호버 툴팁. 지연 숨김, Esc, 화면 밖 보정까지 구현됨 | `hooks/useLinkTooltip.ts`, `LinkTooltip.tsx`, `utils/epubLinkTooltips.ts` |
| EPUB iframe 안에서의 이벤트 처리 | `rendition.hooks.content.register` 에서 장마다 리스너를 붙이는 패턴 | `EpubDocumentView.tsx` |
| 구절 선택 후 질문 | Ask AI, Summarize, 주석, 하이라이트 | `TextSelectionMenu.tsx`, `useChatStore.sendMessage({ quotedText })` |
| 구조화된 LLM 출력 | JSON 응답 강제와 검증 | `ai-service.ts` 의 `generateJsonResponse`, `subscription-client.ts` 의 `responseFormat` |
| 백그라운드 LLM 작업 선례 | 세션 종료 후 메모리 추출 큐, 실패 재시도 | `agent-memory-service.ts`, `memory-extractor.ts` |
| 사용자 프로필 | `USER.md` (Known Strengths, Academic Orientation 등), Hindsight 회상 | `agent-memory-files.ts`, `buildMemoryContextForPrompt` |
| 위치에 붙는 메모 | 본문 위치(anchor)에 고정되는 주석, AI 답변을 주석으로 저장하는 `origin` | `shared/commentary.ts`, `commentary-service.ts` |
| 문서와 장 식별 | `documentHash`, `md:<id>` 또는 `epub:<id>#<chapterHref>` 형태의 컨텍스트 키 | `utils/chat-context.ts` |
| 읽기 위치 신호 | EPUB `relocated` 이벤트, 포커스 모드의 활성 문단 | `EpubDocumentView.tsx` |
| 웹 검색 | TinyFish 검색과 페이지 가져오기 (글만) | `tinyfish-web-search-service.ts` |
| 주석을 EPUB에 넣기 | 주석과 그림 자산을 포함한 EPUB 내보내기 | `commentary-epub.ts`, `commentary-service.ts` |
| 구독 한도 정보 | Claude `quota.utilization`, Codex `usedPercent` | `shared/claude.ts`, `shared/codex.ts` |
| 로컬 저장 | `better-sqlite3` 기반 서비스 여러 개, `SimpleStore` 설정 | `main/*-service.ts`, `simple-store.ts` |

### 설계를 좌우하는 제약 네 가지

1. **LLM은 구독 CLI(Codex, Claude Code)로만 호출된다.** HTTP API도, 로컬 모델도 없다. 0.9.0에서 Ollama를 의도적으로 제거했다. 따라서 "비용"은 금액이 아니라 **구독 한도 소모와 지연 시간**이다.
2. **호출마다 프로세스가 하나씩 뜬다.** Claude 쪽은 매 호출 전에 버전 확인과 인증 상태 확인까지 추가로 실행한다(`ClaudeClient.stream` 의 `inspect`). 그래서 이 앱에서는 작은 호출을 여러 번 하는 것이 유난히 비싸고, **큰 호출 한 번으로 묶는 것이 구조적으로 유리하다.** 문단마다 호출하는 설계는 이 아키텍처와 맞지 않는다.
3. **`ai:chat` 은 창마다 요청 하나만 유지한다.** 새 요청이 오면 이전 요청을 중단시킨다(`activeAiRequests`). 코치의 백그라운드 호출이 이 경로를 쓰면 사용자의 질문을 끊거나 끊기게 된다. 코치는 별도 IPC와 별도 큐를 가져야 한다.
4. **EPUB에서 `tab.content` 는 지금 화면에 보이는 텍스트뿐이다**(`extractVisibleText`). 장 전체 텍스트는 `book.load(...)` 로 스파인 문서를 따로 읽어야 한다. `resolveEpubLink` 가 이미 같은 방식으로 다른 장의 문서를 읽고 있으므로 그대로 따르면 된다.

## 4. 설계

### 4.1 독서 전 코칭 설정

책(EPUB)을 처음 열 때 작은 창 하나로 묻는다. "왜 읽는가", "얼마나 아는가", "얼마나 나설까"를 따로 묻는다. 한 줄에 섞어 묻지 않는 이유는 "익숙한 분야지만 교양으로 가볍게"나 "처음이지만 제대로 공부" 같은 조합이 가능해야 하기 때문이다. 클릭 두세 번이면 끝난다.

**1. 이 책을 어떻게 읽고 싶으세요? (하나 선택)**

| 선택지 | 코치가 하는 일 |
|---|---|
| **훑어보기.** 어떤 책인지 빠르게 파악하고 싶어요 | 장 브리핑과 절마다의 요약을 먼저 보여 주고, 카드는 최소로 |
| **교양으로 즐기기.** 배경과 뒷이야기를 곁들여 읽고 싶어요 | 인물, 시대 배경, 그림이 있는 카드 위주 |
| **제대로 공부하기.** 개념을 하나하나 이해하며 읽고 싶어요 | 용어 풀이, 논증 구조, 장 끝 확인 질문 |
| **따져 가며 읽기.** 저자의 주장을 비판적으로 검토하고 싶어요 | 반론, 다른 해석, 이후 연구에서 달라진 점 |
| **내 연구에 쓰기.** 내 관심사와 닿는 지점을 찾고 있어요 | 다른 분야나 예전에 읽은 책과의 연결. 자유 입력과 함께 쓰기를 권함 |

**2. 이 분야가 얼마나 익숙하세요?**

처음이에요 / 조금 알아요 / 익숙해요 (전공이거나 여러 권 읽음)

**3. 코치가 얼마나 나설까요? (기본값: 조용히)**

부를 때만 / 조용히 표시만 / 먼저 제안하기

**4. 따로 부탁할 것이 있나요? (자유 입력, 선택)**

빈 칸에 예시 문구를 흐리게 보여 준다.

- "철학 용어는 원어를 함께 알려 주세요"
- "신경과학과 연결되는 지점을 짚어 주세요"
- "인물이 나오면 생몰연도와 시대 배경을 꼭 넣어 주세요"
- "수식 유도는 건너뛰고 의미만 설명해 주세요"

맨 아래에는 **"지금은 그냥 읽을게요"** 버튼을 둔다.

1번은 카드의 **종류**를, 2번은 **난이도**를, 3번은 **빈도**를 정한다. 셋 다 로컬 선별의 입력이다.

동작 원칙은 다음과 같다.

- **건너뛸 수 있다.** 맨 아래 버튼을 누르면 코치는 꺼진 채로 열리고, 다시 묻지 않는다. 가볍게 훑어볼 책에서는 아무것도 생성되지 않으므로 LLM 사용도 없다.
- **언제든 바꿀 수 있다.** 읽기 화면 상단과 코치 탭에 같은 창을 여는 버튼을 둔다. 설정에는 "새 책을 열 때 묻기"를 끄는 항목과 기본 선호를 둔다.
- **책마다 저장한다.** `documentHash` 기준으로 저장하고, 새 책에서는 직전 책의 선택을 미리 채워 보여 준다. 대부분은 확인만 누르면 된다.
- **1~3번은 재생성을 일으키지 않는다.** 이 세 답은 이미 만들어진 덱에서 무엇을 드러낼지와 나서는 정도만 바꾼다. 덱에는 처음부터 모든 종류와 수준의 카드, 절 요약이 들어 있기 때문이다. 그래서 읽다가 마음을 바꿔도 즉시 반영되고 추가 호출이 없다.
- **자유 입력은 프롬프트에 그대로 들어간다.** 예를 들어 "신경과학과 연결되는 지점을 짚어 줘"라고 적으면, 그 문장이 이후에 만드는 덱의 생성 지시와 "더 자세히" 답변의 지시에 덧붙는다. 별도의 해석용 호출은 하지 않는다. 이미 만든 장에 반영하고 싶을 때는 "이 장 다시 준비" 버튼으로 그 장만 다시 만든다.
- **나서는 정도의 기본값은 "조용히"** 이고, 3번에서 고른 답이 그 기본값을 덮어쓴다. "부를 때만"을 고르면 본문 표시 없이 코치 탭과 직접 질문만 쓴다. 이 경우에도 덱은 코치 탭을 처음 열 때 만든다.

이 설정이 2단계의 수준 추정에서 "첫 만남 문제"를 해결하는 출발값이 된다(4.5).

### 4.2 카드 덱: 장마다 한 번 만드는 묶음

코치가 켜진 책에서 장에 처음 진입해 일정 시간 머물면, 백그라운드에서 한 번 호출해 아래 JSON을 받는다.

```jsonc
{
  "domain": ["religious studies", "ancient history"],   // 수준을 분야별로 추정하기 위한 태그
  "brief": "이 장을 읽기 전에 알면 좋은 것 3줄",
  "sections": [                                         // 절 앞에 미리 보여 줄 요약
    { "quote": "절 제목 또는 절의 첫 구절", "summary": "이 절의 요지 2~3문장" }
  ],
  "recap": ["핵심 1", "핵심 2", "핵심 3"],
  "questions": ["스스로 확인해 볼 질문 1", "질문 2"],
  "cards": [
    {
      "kind": "term",              // term | person | place | background | math | structure | critique | connection
      "difficulty": 2,             // 1(교양 수준) ~ 5(전공 심화)
      "quote": "the Axial Age",    // 본문에 실제로 나오는 문자열. 위치를 찾는 닻
      "title": "축의 시대",
      "gloss": "두 문장 이내의 설명. 이 책의 맥락에서의 의미.",
      "image_query": "Axial Age Karl Jaspers"   // 선택. 그림이 도움이 되는 카드에만
    }
  ]
}
```

- **모든 수준과 종류의 카드를 한 번에 받는다.** 누구에게 무엇을 보일지는 나중에 로컬에서 거른다. 선호나 수준 추정이 바뀌어도 재호출이 없다.
- **브리핑, 절 요약, 정리, 확인 질문도 같은 호출에 넣는다.**
- **닻 검증.** 돌아온 `quote` 가 장 텍스트에 문자 그대로 존재하지 않으면 그 항목은 버린다. 환각으로 만든 위치를 걸러 내는 값싼 방어다.
- **본문은 신뢰하지 않는 자료로 취급한다.** 기존 시스템 프롬프트와 같은 문구를 쓰고, 카드 텍스트는 기존 `renderCommentary` 처럼 원시 HTML을 버리는 렌더러로 표시한다.
- **장 텍스트 얻기.** `tab.content` 는 보이는 쪽만 담으므로, `resolveEpubLink` 가 하는 것처럼 `book.load(...)` 로 스파인 문서를 읽어 텍스트를 뽑는다.
- **캐시 키**는 `sha256(documentHash + chapterHref + 프롬프트 버전 + 출력 언어 + 자유 입력 문장)`. 같은 책을 다시 열거나 다시 읽어도 호출이 없다.

### 4.3 호버 카드: 글과 그림

첨부하신 Wikipedia 화면과 같은 모양을 목표로 한다. 위쪽에 그림, 아래에 짧은 설명, 맨 아래에 버튼 줄.

- 버튼: **더 자세히** (채팅 패널에서 본격 설명), **EPUB에 넣기** (주석으로 저장), **이미 알아요**, **이런 건 그만**.
- 글은 덱에 이미 들어 있으므로 즉시 뜬다. 그림은 처음 열 때 한 번 가져오고 이후에는 캐시에서 나온다. 그림이 늦으면 글 먼저 보이고 그림이 나중에 채워진다.
- 기존 `LinkTooltip` 과 `createEpubLinkTooltips` 를 확장해 만든다. iframe 좌표 변환, 지연 숨김, Esc 처리가 이미 되어 있다.

**본문 표시 방식.** EPUB 본문은 epub.js iframe 안에 있다. 여기에 `<span>` 을 끼워 넣으면 기존 하이라이트(`rendition.annotations`)와 주석 닻(`CommentaryAnchor.path` 는 DOM 경로다)을 어긋나게 할 위험이 있다. 그래서 DOM을 건드리지 않는 **CSS Custom Highlight API**(`CSS.highlights` 와 `::highlight()`)를 권한다. `Range` 만 등록해 점선 밑줄을 그리고, 호버 판정은 `pointermove` 에서 Range의 사각형과 좌표를 비교한다. Electron 34의 Chromium에서 지원되지만, iframe 안과 양면(spread) 보기에서 잘 동작하는지는 0단계에서 먼저 확인한다. 등록은 이미 있는 `rendition.hooks.content.register` 에서 장이 그려질 때마다 한다.

한 화면에 드러나는 표시는 상한을 둔다(기본 쪽당 4개 안팎). 같은 용어는 장에서 처음 나올 때만 표시한다.

### 4.4 그림을 어디서 가져오나: TinyFish 확인 결과

**결론: TinyFish 검색만으로는 그림을 가져올 수 없다. TinyFish로 "맞는 Wikipedia 문서"를 찾고, 그림은 Wikipedia에서 가져오는 두 단계 구성이 현실적이다.**

확인한 내용은 이렇다.

- TinyFish Search API 문서를 보면 검색 종류는 `web`, `news`, `research_paper` 세 가지뿐이고 이미지 검색이 없다. 결과 항목에도 그림이나 썸네일 필드가 없다(제목, 요약, URL, 날짜 등만 있다).
- 현재 앱의 `tinyfish-web-search-service.ts` 도 제목, URL, 요약만 받는다.
- 다만 검색 API에는 `include_domains` 가 있어 결과를 `wikipedia.org` 로 한정할 수 있다. 현재 코드는 이 인자를 쓰지 않으므로 추가해야 한다.
- TinyFish Fetch API는 페이지를 Markdown으로 돌려준다. 그 안에 그림 주소가 남아 있는지는 문서로 확인하지 못했다. 0단계에서 실제로 호출해 본다.

제안하는 흐름은 다음과 같다.

1. 카드의 `image_query` 로 TinyFish 검색을 `wikipedia.org` 한정으로 실행해 해당 문서 주소를 얻는다. 검색 호출 1회이고 LLM은 쓰지 않는다. 동명이인이나 다의어도 검색어에 맥락이 들어 있어 대체로 가려진다.
2. 그 문서의 대표 그림을 Wikipedia의 공개 요약 API에서 받는다. 이 API는 대표 그림 주소와 문서 요약을 함께 준다. 키가 필요 없고 무료다. Fetch 결과에 그림 주소가 들어 있는 것으로 확인되면 이 단계를 Fetch로 대신할 수도 있다.
3. 메인 프로세스에서 그림을 내려받아 크기를 줄이고 `coach.sqlite` 에 저장한다. 렌더러에는 data URL로 넘긴다. 기존 주석 그림과 같은 방식이다.

지켜야 할 점.

- **그림은 열어 본 카드에 대해서만 가져온다.** 덱을 만들 때 30~40장의 그림을 미리 받지 않는다. TinyFish 호출 수와 외부 전송을 줄이기 위해서다. 한 번 받은 그림은 용어 단위로 캐시해 다른 책에서도 다시 쓴다.
- **TinyFish 키가 없거나 웹 검색이 꺼져 있으면** 그림 없이 글만 보여 준다. 기능 전체가 멈추지 않는다.
- **외부로 나가는 것은 검색어뿐**이다. 본문이나 사용자 정보는 보내지 않는다.
- **출처와 라이선스.** Wikipedia 그림은 대부분 자유 라이선스지만 출처 표시가 필요하다. 카드 아래에 출처 링크를 두고, EPUB에 넣을 때는 출처 줄을 함께 넣는다.
- **틀린 그림 방지.** 대표 그림이 없거나 검색 결과가 카드 제목과 맞지 않으면 그림을 생략한다. 틀린 그림보다 그림 없음이 낫다.

### 4.5 EPUB에 넣기

이미 있는 주석 기능을 그대로 쓴다. 카드에서 "EPUB에 넣기"를 누르면 그 카드의 닻 위치에 주석이 만들어지고, 기존 "주석을 포함한 EPUB 저장"으로 책 안에 들어간다.

- 카드의 글은 주석의 `markdown` 으로, 그림은 주석 자산(`mdr-asset:`)으로 저장한다. 지금의 `importCommentaryImage` 는 파일 선택 창에서 고른 파일만 받으므로, 이미 받은 그림 데이터를 자산으로 등록하는 경로를 하나 추가한다. 검증 규칙(PNG 변환, 8MB 한도, 해시 ID)은 그대로 따른다.
- 주석의 `origin` 에 코치가 만든 것임을 남겨 "내 주석"과 구분되게 한다.
- "더 자세히"로 받은 긴 답변도 지금처럼 채팅에서 주석으로 옮길 수 있다.
- 나중 단계에서는 "이 장에서 열어 본 카드 모두 넣기" 같은 묶음 동작을 더할 수 있다.

### 4.6 LLM 사용량: 네 단계로 나누기

| 단계 | 무엇을 | LLM 호출 | 언제 |
|---|---|---|---|
| 0. 호출 없음 | 카드 선별, 수준 추정, 막힘 감지, 캐시 조회, 그림(TinyFish + Wikipedia), 내가 예전에 남긴 주석, 다른 책에서 만든 같은 용어 카드 | 없음 | 항상 |
| 1. 장 덱 | 카드 덱 생성 | 장당 1회 | 코치가 켜진 책에서 장에 머물 때, 백그라운드 |
| 2. 깊은 설명 | "더 자세히", "이 문단 풀어 줘" | 수락 1회당 1회 | 사용자가 눌렀을 때만 |
| 3. 선택 기능 | 책 전체 미리 준비, 복습 퀴즈, "이 장 다시 준비" | 사용자가 요청한 경우만 | 명시적 요청 |

**코치 전용 모델.** 정해 주신 대로 Claude 구독에서는 `claude:sonnet`, Codex 구독에서는 GPT-6.2 Sol을 기본값으로 한다. Codex 쪽 모델 ID는 계정의 모델 목록에서 받아 오는 값이므로(`listSubscriptionModels`), 설정에서 목록 중 하나를 고르는 방식으로 두고 기본 선택만 맞춰 둔다. 사용자가 고른 채팅 모델의 제공자와 같은 쪽을 따른다.

가장 저렴한 모델이 아니라 중간급 모델을 쓰는 만큼, 호출 횟수를 묶는 장치가 더 중요해진다.

**규모 감각(추정치이며 0단계에서 실측한다).** 300쪽짜리 책이 15장이라면 책 한 권을 다 읽는 동안 백그라운드 호출은 15회 정도다. 문단마다 제안을 생성하는 방식이라면 같은 책에 천 번 이상이 든다. 이 앱은 호출마다 CLI 프로세스를 띄우므로 장 단위로 묶는 쪽이 구조적으로도 맞다.

**사용량을 묶어 두는 장치.**

- **코치를 켠 책에서만 생성한다.** 독서 전 설정에서 건너뛴 책은 호출이 0이다.
- **지연 생성.** 장에 들어와 수십 초 머문 뒤에야 생성한다. 목차를 훑어 넘기는 것만으로는 호출되지 않는다. 미리 만드는 범위는 현재 장과 다음 장까지만.
- **하루 상한.** 백그라운드 덱 생성 횟수의 일일 한도(기본 20회 안팎). 초과하면 조용히 멈추고 코치 탭에 표시한다.
- **한도 인식.** 구독 사용률이 일정 수준(예: 70%)을 넘으면 백그라운드 생성을 멈춘다. 사용자의 직접 질문이 항상 우선이다.
- **직렬화.** 동시 실행 1개. 사용자의 채팅이 스트리밍 중이면 대기한다. `ai:chat` 과 다른 IPC, 다른 중단 제어를 쓴다.
- **긴 장 나누기.** 일정 분량(예: 6천 단어)을 넘으면 절 단위로 나누고, 읽고 있는 절부터 만든다.
- **투명성.** 설정 화면에 "오늘 코치가 쓴 호출 수"와 "캐시에서 해결한 횟수"를 보여 준다.

**로컬 모델에 대하여.** Ollama는 직전 릴리스에서 걷어냈으므로 코치를 위해 다시 들이는 것은 권하지 않는다. 대신 LLM이 아닌 로컬 계산(선별, 추정, 감지, 캐시)을 적극적으로 쓴다.

### 4.7 수준과 취향 추정

출발값은 4.1의 독서 전 설정이다. 그 뒤로 아래 사건을 기록해 다듬는다.

| 사건 | 의미 | 신호의 세기 |
|---|---|---|
| 카드를 열어 봄 (호버 유지) | 약한 관심 | 약한 긍정 |
| "더 자세히" 누름 | 필요했음 | 강한 긍정 |
| "EPUB에 넣기" | 가치 있었음 | 가장 강한 긍정 |
| "이미 알아요" | 너무 쉬움 | 난이도 축에 대한 부정 (수준을 올림) |
| "이런 건 그만" | 종류가 안 맞음 | 종류 축에 대한 부정 |
| 그냥 닫음 | 모호함 | 약한 부정 |
| 표시됐지만 지나침 | 매우 모호함 | 거의 반영하지 않음 |
| 카드가 없던 구절을 선택해 Ask AI | 코치가 놓침 | 그 난이도의 문턱을 낮춤 |

거절을 두 버튼으로 나누는 것이 요점이다. 단순히 "닫음"만 세면 "쉬워서"인지 "관심 없어서"인지 "바빠서"인지 구분할 수 없고, 추정이 엉뚱한 방향으로 흘러간다. 마지막 줄의 "놓침" 신호도 중요하다. 지금의 질문 창 사용 기록이 그대로 코치의 학습 자료가 된다.

**모델.** 처음부터 복잡하게 가지 않는다.

- (분야 × 카드 종류 × 난이도 구간)별로 수락과 거절의 가중 횟수를 센다. 베타 분포의 두 숫자다. 독서 전 설정은 이 숫자의 초깃값으로 들어간다.
- 카드를 보일지는 그 칸의 수락 확률 추정치가 문턱을 넘는지로 정한다. 가끔은 문턱 아래 카드도 일부러 하나씩 보여 준다(탐색). 그래야 한번 굳어진 추정을 바로잡을 기회가 생긴다.
- 오래된 기록은 서서히 가중치를 줄인다. 사람은 책을 읽으며 성장한다.
- 수준은 **분야별**로 둔다. 덱 호출이 돌려주는 `domain` 태그를 쓴다.

**사용자가 정한 것이 추정보다 우선한다.** 독서 전 설정에서 명시적으로 고른 것은 추정이 뒤집지 않는다. 추정은 그 안에서의 미세 조정만 한다. 추정이 설정과 크게 어긋나 보이면("처음이라고 하셨는데 기초 카드를 계속 넘기시네요. 줄일까요?") 스스로 바꾸지 않고 한 번 물어본다. 코치 탭에는 "코치가 추정한 수준"을 보여 주고 직접 고칠 수 있게 한다. 사건 기록은 기기 안의 SQLite에만 남긴다.

**막힘 감지.** 문단 길이로 예상 읽기 시간을 계산하고(이미 분당 200단어 기준이 있다), 실제 체류가 그 몇 배를 넘거나 앞쪽으로 되돌아가면 "막힘"으로 본다. EPUB의 `relocated` 이벤트와 포커스 모드의 활성 문단을 쓴다. 막힘이 감지돼도 LLM을 부르지 않는다. 그 문단에 붙은 카드를 드러내거나 "풀어 드릴까요?" 칩을 띄울 뿐이고, 호출은 사용자가 누른 뒤에 일어난다.

### 4.8 얼마나 나설 것인가

| 단계 | 동작 |
|---|---|
| 끔 | 지금과 동일. 독서 전 설정을 건너뛰면 이 상태 |
| 부를 때만 | 본문 표시 없음. 코치 탭에서 카드 목록을 직접 열어 봄 |
| 조용히 (기본값) | 본문 밑줄과 호버 카드만. 먼저 말을 걸지 않음 |
| 제안 | 여백 칩, 막힘 감지 제안, 장 앞 브리핑과 절 요약 추가 |
| 적극 | 확인 질문과 반론 카드까지 적극적으로 |

독서 전 설정의 3번 답이 이 단계를 정한다. "먼저 제안하기"는 "제안"에 해당하고, "적극"은 설정에서 따로 켠다. 3번을 건드리지 않으면 "조용히"다. "훑어보기"를 고른 경우에는 단계와 무관하게 절 요약과 장 브리핑을 보여 준다.

먼저 말을 거는 제안에는 규칙을 둔다. 문단 중간에는 끼어들지 않고 쪽 넘김 같은 경계에서만 나타난다. 일정 시간에 하나만 띄운다. 연속으로 몇 번 거절당하면 그 세션에서는 스스로 조용해진다. 포커스 모드에서는 여백 칩만 쓰고 팝업은 띄우지 않는다.

기존 흐름과의 연결은 세 군데다. "더 자세히"는 `sendMessage({ quotedText })` 를 그대로 부르되 선호와 추정 수준을 한 줄 덧붙인다. "EPUB에 넣기"는 기존 주석 저장 경로를 쓴다. `TextSelectionMenu` 의 Ask AI는 "놓침" 사건을 기록한다.

## 5. 단계별 구현

각 단계는 그 자체로 쓸 수 있는 상태에서 끝나도록 나눴다. 모든 단계는 EPUB만 대상으로 한다.

### 0단계: 검증 (작게, 먼저)

- EPUB 한 장으로 덱 생성 프롬프트를 실제로 돌려 본다. `claude:sonnet` 과 GPT-6.2 Sol 각각에서 지연 시간, 구독 사용률 변화, 카드 품질, 닻 검증 통과율을 잰다.
- CSS Custom Highlight API가 epub.js iframe 안에서, 양면 보기와 주석 읽기 보기에서 동작하는지, 기존 하이라이트와 겹쳐도 괜찮은지 확인한다. 안 되면 span 삽입 방식과 주석 닻의 충돌 여부를 살핀다.
- 그림 경로를 실제로 호출해 본다. TinyFish 검색의 `include_domains`, Fetch 결과에 그림 주소가 남는지, Wikipedia 대표 그림의 적중률.
- 통과 기준: 덱 하나가 감당할 만한 시간과 사용률 안에 만들어지고, 카드의 대부분이 닻 검증을 통과할 것.

### 1단계: 묻고, 조용히 돕는 코치 (첫 출시 범위)

- 독서 전 설정 창(읽는 목적, 익숙한 정도, 나서는 정도, 자유 입력, 건너뛰기, 나중에 바꾸기).
- 덱 생성, 캐시, 작업 큐, 하루 상한.
- 본문 밑줄과 호버 카드(글만). 카드의 네 버튼. "EPUB에 넣기"는 글만.
- 절 앞 요약과 장 앞 브리핑(덱에 이미 들어 있으므로 표시만 하면 된다).
- 사건 기록은 시작하되 아직 추정에는 쓰지 않는다. 선별은 독서 전 설정만으로 한다.

### 2단계: 그림이 있는 카드

- TinyFish로 문서 찾기, 그림 내려받기와 캐시, 카드에 그림 표시, 출처 표기.
- "EPUB에 넣기"에 그림과 출처 줄 포함.

### 3단계: 배우는 코치

- 사건 기록으로 분야별 수준과 종류별 취향을 추정하고 선별에 반영한다.
- Ask AI의 "놓침" 신호 연결.
- 추정 수준 표시와 수동 조정, 설정과 어긋날 때 되묻기.

### 4단계: 먼저 말 거는 코치

- 여백 칩, 막힘 감지, 장 뒤 정리와 확인 질문.
- 빈도 제한과 스스로 조용해지는 규칙.
- 채팅 패널의 코치 탭, 사용량 표시, 구독 한도 연동 일시 정지.

### 5단계: 기억과 연결

- 책을 넘나드는 용어와 그림 캐시 재사용, 내 주석과 예전 질문 답변을 카드로 끌어오기.
- 코치 프로필 요약을 `USER.md` 와 Hindsight에 반영해 채팅 답변의 눈높이도 함께 맞춘다.
- "연결자" 카드를 Hindsight 회상으로 실제 내 독서 이력과 잇는다.
- "이 장에서 열어 본 카드 모두 EPUB에 넣기", 확인 질문의 간격 복습.

## 6. 위험과 대응

| 위험 | 대응 |
|---|---|
| 카드 내용이 틀림 | 설명은 두 문장 이내로 짧게, "이 책의 맥락에서"로 한정. AI가 만든 것임을 표시. 깊은 설명에서는 기존 웹 검색 옵션 사용 가능 |
| 그림이 엉뚱함 | 검색 결과 제목과 카드 제목을 대조. 맞지 않으면 그림 생략. 출처 링크 표시 |
| 그림 라이선스 | 출처와 함께 저장하고 EPUB에 넣을 때 출처 줄 포함. 내보낸 EPUB을 배포할 경우의 책임은 사용자에게 있음을 안내 |
| 위치가 어긋남 | 닻 문자열 검증. 못 찾으면 버림. DOM을 바꾸지 않는 표시 방식 |
| 방해가 됨 | 기본값은 "조용히". 표시 상한, 빈도 제한, 연속 거절 시 침묵 |
| 구독 한도를 갉아먹음 | 켠 책에서만, 장당 1회, 하루 상한, 사용률 기준 정지, 사용자 질문 우선, 사용량 공개 |
| 추정이 한쪽으로 굳음 | 명시적 설정 우선, 거절 사유 분리, 탐색용 카드, 시간에 따른 감쇠, 수동 조정 |
| 백그라운드 작업이 채팅을 끊음 | 별도 IPC, 별도 중단 제어, 직렬 큐 |

## 7. 결정된 것과 남은 것

**결정됨 (2026-11-19).**

1. 적용 범위는 EPUB만.
2. 코치 전용 모델은 Claude에서 `sonnet`, Codex에서 GPT-6.2 Sol.
3. 호버 카드는 Wikipedia 미리보기 형태. 그림을 함께 보여 주고, 원하면 기존 주석 기능으로 EPUB에 넣는다.
4. 책을 읽기 전에 원하는 코칭을 묻는다. 읽는 목적 다섯 가지 중 하나, 분야에 익숙한 정도, 나서는 정도, 자유 입력. 건너뛰기 가능, 언제든 변경 가능.
5. 나서는 정도의 기본값은 "조용히". 독서 전 설정의 답이 이를 덮어쓴다.

**0단계에서 확인할 것.**

1. 그림 경로의 세부. TinyFish 검색은 그림을 주지 않으므로 Wikipedia에서 그림을 받는 단계가 필요하다. Fetch 결과만으로 되는지, Wikipedia 요약 API를 직접 부를지는 실제 호출로 정한다.
2. iframe 안에서의 표시 방식(Custom Highlight API 또는 span).
3. 두 모델에서의 덱 생성 시간과 사용률.

## 8. 구현 현황 (2026-11-19)

이 계획에 따라 1~3단계와 4단계 일부를 구현했다.

**구현됨**

- 1단계: 독서 전 설정 창(읽는 목적, 익숙한 정도, 나서는 정도, 자유 입력, "지금은 그냥 읽을게요"), 읽기 화면 아래 "코치" 버튼으로 언제든 변경. 책마다 저장하고 직전 책의 선택을 미리 채움. 장마다 1회 덱 생성(20초 머문 뒤), `coach.sqlite` 캐시, 직렬 작업 큐(최근 3개까지만 대기), 하루 상한, 구독 사용률 기준 정지, 사용자의 채팅이 진행 중이면 대기. 닻 검증. 6천 단어가 넘는 장은 나눠서 읽고 있는 부분부터 생성. CSS Custom Highlight API로 본문 점선 밑줄(DOM 변경 없음), Wikipedia식 호버 카드와 네 버튼. 장 브리핑, 화면에 보이는 절의 요약, 장 끝 정리와 확인 질문(“먼저 제안하기” 또는 “훑어보기”일 때).
- 2단계: TinyFish 검색을 `include_domains=wikipedia.org` 로 한정해 문서를 찾고, Wikipedia 요약 API의 대표 그림을 `upload.wikimedia.org` 에서만 받아 480px PNG로 줄여 검색어 단위로 캐시. 제목이 맞지 않거나 동음이의 문서면 그림 생략. "EPUB에 넣기"는 그림을 주석 자산으로 등록하고 출처 줄을 함께 넣음(`commentary:image-data`).
- 3단계: 이벤트 기록과 분야별 (난이도 구간, 카드 종류) 베타 카운트, 60일 반감기, 독서 전 설정 대비 ±0.3 안에서만 조정, 가끔 문턱 아래 카드 1장 탐색, Ask AI "놓침" 신호, 설정과 어긋나면 한 번 묻기, 코치 탭의 추정 수준 표시와 초기화.
- 4단계 일부: 채팅 패널의 "코치" 탭(숨은 카드 포함 전체 목록, 절 요약, 정리, 질문, "이 장 다시 준비", 사용량), 설정의 "독서 코치" 구역(새 책에서 묻기, 코치 모델, 하루 한도, 정지 사용률, 오늘 사용량).

**남은 것**

- 0단계 실측: 실제 구독 계정으로 두 모델의 덱 생성 시간·사용률·닻 통과율 측정, Wikipedia 대표 그림 적중률. (CSS Custom Highlight 밑줄과 요소를 가로지르는 구절의 호버 판정은 Chromium에서 확인했으나 epub.js 양면·주석 읽기 보기에서는 앱에서 확인 필요.)
- 4단계: 여백 칩, 막힘 감지 제안, 빈도 제한·스스로 조용해지기, "적극" 단계 선택 UI, 다음 장 미리 준비.

**5단계 (2026-11-19 추가 구현)**

- 책을 넘나드는 재사용: 덱이 만들어지면 용어(본문 구절 정규화)를 `coach_terms` 에 남긴다. 다른 책에서 같은 용어를 만나면 카드에 "다른 책에서도 만났어요: 《…》"를 보여 주고, 그 책에서 "이미 알아요"를 눌렀던 용어는 본문에 다시 표시하지 않는다. 그림은 처음부터 검색어 단위로 캐시되어 책과 무관하게 재사용된다. 모델 호출 없음.
- 내 기록 끌어오기: 카드 용어가 들어간 예전 질문(그 질문에 대한 첫 답 포함)과 내 주석(코치 카드는 제외)을 찾아 카드와 코치 탭에 보여 준다. 로컬 SQLite 검색만 한다.
- 코치 프로필 반영: 사건이 기록되면 1분 뒤 한 번, 추정 수준과 선호·회피 카드 종류를 `USER.md` 의 "Reading Coach Profile" 구역에 다시 쓴다(덧붙이지 않고 교체). 하루 한 번까지 같은 문서 ID(`md-reader-coach-profile`)로 Hindsight에 보내 이전 판을 대체한다. 채팅 프롬프트의 메모리 블록에 이 구역을 따로 넣어 답변의 눈높이도 맞춘다. 메모리가 꺼져 있으면 아무것도 하지 않는다.
- 연결자: 코치 탭을 열면 장 제목, 분야, 주요 카드 제목으로 Hindsight 회상을 한 번 하고(LLM 생성 없음, budget low) 결과 3개를 "장기 기억에서"로 보여 준다. 장마다 7일 캐시.
- "이 장에서 열어 본 카드 모두 EPUB에 넣기": 열어 봤거나 "더 자세히"를 누른 카드 중 아직 주석이 아닌 것을 그림과 함께 한 번에 주석으로 저장한다.
- 간격 복습: 장 끝에 이르면 그 장의 확인 질문을 복습 목록에 넣는다(내일부터). 코치 탭에서 "기억나요"(1→3→7→16→35→80일), "가물가물해요"(내일 다시), "답 확인"(장 요점과 함께 채팅으로 질문).

**남은 것 (5단계 이후)**

- 실제 앱과 계정에서의 확인: Hindsight 회상 품질, 프로필 요약 문구, 복습 알림을 책을 열지 않았을 때도 보여 줄지.
