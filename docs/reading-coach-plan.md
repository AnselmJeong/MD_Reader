# Proactive 독서 코치 계획서

작성일: 2026-11-19 · 기준 버전: 0.9.0 (`27eec12`) · 상태: 제안 (코드 변경 없음)

## 1. 한 줄 결론

구현할 수 있고, LLM을 과하게 쓰지 않고도 할 수 있다. 핵심은 **"독자가 읽는 순간마다 LLM을 부르는 코치"가 아니라 "장(chapter)마다 한 번 미리 카드 묶음을 만들어 두고, 누구에게 무엇을 보여줄지는 LLM 없이 로컬에서 고르는 코치"** 로 설계하는 것이다.

- 장 하나당 백그라운드 LLM 호출 1회로 "카드 덱"(용어, 배경, 논증 구조, 반론, 연결 등 30~40장)을 만들어 SQLite에 영구 캐시한다.
- 화면에 어떤 카드를 드러낼지는 사용자 수준 모델이 로컬에서 결정한다. 여기에는 LLM이 전혀 들지 않는다.
- 사용자가 카드를 열고 "더 자세히"를 누를 때만 지금의 질문 창과 같은 본격 호출이 일어난다. 즉 비싼 호출은 항상 사용자의 명시적 수락 뒤에 온다.
- 수락과 거절 이력으로 수준과 취향을 추정하되, 거절의 이유("이미 알아요"와 "이런 종류는 관심 없어요")를 구분해서 받는다.

## 2. 상상: 어떤 경험인가

같은 책, 같은 문단을 두 사람이 읽는다고 하자.

**초심자.** 장을 열면 상단에 세 줄짜리 "이 장을 읽기 전에"가 접힌 채로 놓여 있다. 본문에는 페이지당 서너 군데에 옅은 점선 밑줄이 있다. "축의 시대"에 마우스를 올리면 Wikipedia 미리보기처럼 두 문장짜리 설명이 즉시 뜬다. 즉시 뜨는 이유는 이미 만들어 둔 카드이기 때문이다. 한 문단에서 유난히 오래 머물면 여백에 작은 칩이 조용히 나타난다. "이 문단, 풀어서 설명해 드릴까요?" 누르면 그때 비로소 AI가 답을 쓴다. 장이 끝나면 "핵심 세 가지와 스스로 확인해 볼 질문 두 개"가 기다린다.

**전문가.** 같은 문단에서 "축의 시대" 밑줄은 보이지 않는다. 기초 용어 카드는 수준 필터에서 걸러졌기 때문이다. 대신 여백에 다른 종류의 칩이 있다. "이 주장에 대한 대표적 반론", "지난달 읽은 다른 책의 3장과 맞닿는 지점". 전문가에게 코치는 설명해 주는 사람이 아니라 옆에서 토를 달아 주는 동료다.

중요한 점은 수준에 따라 **양만 달라지는 것이 아니라 카드의 종류가 달라진다**는 것이다. 그래서 카드에 "난이도"와 "종류" 두 축을 모두 붙인다.

### 코치의 네 가지 역할 (카드 종류)

| 역할 | 카드 종류 | 주로 누구에게 |
|---|---|---|
| 해설자 | 용어 정의, 인물, 역사적 배경, 수식 풀이 | 초심자 |
| 길잡이 | 논증 구조("여기서 저자는 A를 전제로 B를 주장"), 앞 장과의 연결 | 초심자~중급 |
| 반론자 | 비판, 대안 해석, 이후 연구에서 뒤집힌 점 | 중급~전문가 |
| 연결자 | 다른 분야, 다른 책, 내가 남긴 메모와의 연결 | 전문가, 다각적 독서를 원하는 독자 |

### 코치가 나타나는 다섯 자리

1. **본문 밑줄 + 호버 카드.** Wikipedia식. 특정 단어나 구절에 붙는 카드.
2. **여백 칩.** 특정 단어가 아니라 문단 전체에 붙는 카드(논증 구조, 반론, 연결).
3. **장 앞 브리핑과 장 뒤 정리.** 미리 알면 좋은 것, 읽고 난 뒤 확인 질문.
4. **막힘 감지 제안.** 한 문단에 오래 머물거나 되돌아갈 때 뜨는 "풀어 드릴까요?".
5. **코치 탭.** 채팅 패널 안에 이 장의 카드 전체 목록. 걸러져서 안 보이는 카드도 여기서는 볼 수 있다.

## 3. 현재 코드가 이미 제공하는 것

검토 결과, 필요한 부품의 절반 이상이 이미 있다.

| 필요한 것 | 이미 있는 것 | 위치 |
|---|---|---|
| 호버 카드 UI | 링크와 인용에 대한 호버 툴팁. 지연 숨김, Esc, 화면 밖 보정까지 구현됨 | `hooks/useLinkTooltip.ts`, `LinkTooltip.tsx`, `utils/epubLinkTooltips.ts` |
| EPUB iframe 안에서의 이벤트 처리 | `rendition.hooks.content.register` 에서 장마다 리스너를 붙이는 패턴 | `EpubDocumentView.tsx` |
| 구절 선택 후 질문 | Ask AI, Summarize, 주석, 하이라이트 | `TextSelectionMenu.tsx`, `useChatStore.sendMessage({ quotedText })` |
| 구조화된 LLM 출력 | JSON 응답 강제와 검증 | `ai-service.ts` 의 `generateJsonResponse`, `subscription-client.ts` 의 `responseFormat` |
| 백그라운드 LLM 작업 선례 | 세션 종료 후 메모리 추출 큐, 실패 재시도 | `agent-memory-service.ts`, `memory-extractor.ts` |
| 사용자 프로필 | `USER.md` (Known Strengths, Academic Orientation 등), Hindsight 회상 | `agent-memory-files.ts`, `buildMemoryContextForPrompt` |
| 위치에 붙는 메모 | 본문 위치(anchor)에 고정되는 주석, AI 답변을 주석으로 저장하는 `origin` | `shared/commentary.ts`, `commentary-service.ts` |
| 문서와 장 식별 | `documentHash`, `md:<id>` 또는 `epub:<id>#<chapterHref>` 형태의 컨텍스트 키 | `utils/chat-context.ts` |
| 읽기 위치 신호 | 포커스 모드의 활성 문단, 스크롤 진행률, EPUB `relocated` 이벤트 | `hooks/useParagraphFocus.ts`, `EpubDocumentView.tsx` |
| 구독 한도 정보 | Claude `quota.utilization`, Codex `usedPercent` | `shared/claude.ts`, `shared/codex.ts` |
| 로컬 저장 | `better-sqlite3` 기반 서비스 여러 개, `SimpleStore` 설정 | `main/*-service.ts`, `simple-store.ts` |

### 설계를 좌우하는 제약 네 가지

1. **LLM은 구독 CLI(Codex, Claude Code)로만 호출된다.** HTTP API도, 로컬 모델도 없다. 0.9.0에서 Ollama를 의도적으로 제거했다. 따라서 "비용"은 금액이 아니라 **구독 한도 소모와 지연 시간**이다.
2. **호출마다 프로세스가 하나씩 뜬다.** Claude 쪽은 매 호출 전에 버전 확인과 인증 상태 확인까지 추가로 실행한다(`ClaudeClient.stream` 의 `inspect`). 그래서 이 앱에서는 작은 호출을 여러 번 하는 것이 유난히 비싸고, **큰 호출 한 번으로 묶는 것이 구조적으로 유리하다.** 문단마다 호출하는 설계는 이 아키텍처와 맞지 않는다.
3. **`ai:chat` 은 창마다 요청 하나만 유지한다.** 새 요청이 오면 이전 요청을 중단시킨다(`activeAiRequests`). 코치의 백그라운드 호출이 이 경로를 쓰면 사용자의 질문을 끊거나 끊기게 된다. 코치는 별도 IPC와 별도 큐를 가져야 한다.
4. **EPUB에서 `tab.content` 는 지금 화면에 보이는 텍스트뿐이다**(`extractVisibleText`). 장 전체 텍스트는 `book.load(...)` 로 스파인 문서를 따로 읽어야 한다. `resolveEpubLink` 가 이미 같은 방식으로 다른 장의 문서를 읽고 있으므로 그대로 따르면 된다.

## 4. 설계

### 4.1 카드 덱: 장마다 한 번 만드는 묶음

장(또는 Markdown의 큰 절)에 처음 진입해 일정 시간 머물면, 백그라운드에서 한 번 호출해 아래 JSON을 받는다.

```jsonc
{
  "domain": ["religious studies", "ancient history"],   // 수준을 분야별로 추정하기 위한 태그
  "brief": "이 장을 읽기 전에 알면 좋은 것 3줄",
  "recap": ["핵심 1", "핵심 2", "핵심 3"],
  "questions": ["스스로 확인해 볼 질문 1", "질문 2"],
  "cards": [
    {
      "kind": "term",              // term | person | background | math | structure | critique | connection
      "difficulty": 2,             // 1(교양 수준) ~ 5(전공 심화)
      "quote": "the Axial Age",    // 본문에 실제로 나오는 문자열. 위치를 찾는 닻
      "title": "축의 시대",
      "gloss": "두 문장 이내의 설명. 이 책의 맥락에서의 의미.",
      "wiki": "Axial Age"          // 선택. 있으면 Wikipedia 요약을 무료로 덧붙일 수 있음
    }
  ]
}
```

원칙은 다음과 같다.

- **모든 수준의 카드를 한 번에 받는다.** 초심자용과 전문가용을 따로 생성하지 않는다. 누구에게 무엇을 보일지는 나중에 로컬에서 거른다. 그래서 사용자의 수준 추정이 바뀌어도 재호출이 없다.
- **브리핑, 정리, 확인 질문도 같은 호출에 넣는다.** 별도 호출을 만들지 않는다.
- **닻 검증.** 돌아온 `quote` 가 장 텍스트에 문자 그대로 존재하지 않으면 그 카드는 버린다. 환각으로 만든 위치를 걸러 내는 값싼 방어다.
- **본문은 신뢰하지 않는 자료로 취급한다.** 기존 시스템 프롬프트와 같은 문구를 쓰고, 카드 텍스트는 기존 `renderCommentary` 처럼 원시 HTML을 버리는 렌더러로 표시한다.
- **캐시 키**는 `sha256(documentHash + chapterHref + 프롬프트 버전 + 출력 언어)`. 같은 책을 다시 열거나 다시 읽어도 호출이 없다.

### 4.2 본문에 표시하기

Markdown 본문은 `dangerouslySetInnerHTML` 로 렌더링되고, EPUB은 epub.js iframe 안에 있다. 여기에 `<span>` 을 끼워 넣으면 재렌더링 때 지워지거나 기존 하이라이트, 검색 표시(`searchDom.ts` 의 `<mark>` 삽입)와 충돌한다.

권장안은 **CSS Custom Highlight API**(`CSS.highlights` 와 `::highlight()`)다. DOM을 건드리지 않고 `Range` 만 등록해 점선 밑줄을 그린다. Electron 34의 Chromium에서 지원된다. 호버 판정은 `pointermove` 에서 등록된 Range의 사각형과 좌표를 비교하면 되고, 페이지당 표시가 몇 개뿐이라 부담이 없다. 호버 카드 자체는 `LinkTooltip` 을 확장해 재사용한다.

EPUB iframe 안에서도 같은 방식이 동작하는지는 0단계에서 먼저 확인한다. 안 되면 대안은 `hooks.content` 에서 span으로 감싸는 방식이다.

한 화면에 드러나는 표시는 상한을 둔다(기본 페이지당 4개 안팎). 같은 용어는 장에서 처음 나올 때만 표시한다.

### 4.3 LLM 사용량: 네 단계로 나누기

| 단계 | 무엇을 | LLM 호출 | 언제 |
|---|---|---|---|
| 0. 무료 | 문서 안의 각주와 참고문헌(이미 구현), 내가 예전에 남긴 주석과 질문 답변, 다른 책에서 이미 만들어 둔 같은 용어의 카드, Wikipedia 요약 | 없음 | 항상 |
| 1. 장 덱 | 카드 덱 생성 | 장당 1회, 저렴한 모델 | 장에 진입해 머물 때, 백그라운드 |
| 2. 깊은 설명 | "더 자세히", "이 문단 풀어 줘" | 수락 1회당 1회, 사용자가 고른 모델 | 사용자가 눌렀을 때만 |
| 3. 선택 기능 | 책 전체 미리 준비, 복습 퀴즈 | 사용자가 켠 경우만 | 명시적 요청 |

**규모 감각(추정치이며 0단계에서 실측한다).** 300쪽짜리 책이 15장이라면 책 한 권을 다 읽는 동안 백그라운드 호출은 15회 정도다. 문단마다 제안을 생성하는 방식이라면 같은 책에 천 번 이상이 든다. 또한 지금의 질문 창은 Markdown 문서에서 질문할 때마다 문서 전체를 시스템 프롬프트에 붙여 보낸다(`useChatStore.sendMessage`). 즉 **Markdown 문서 하나의 덱을 만드는 입력 비용은 지금 질문 한 번을 던지는 것과 비슷한 수준**이다.

**사용량을 묶어 두는 장치.**

- **코치 전용 모델 설정.** 기본값은 저렴한 쪽(`claude:haiku` 등), 사고 수준은 낮게. 깊은 설명은 사용자가 평소 쓰는 모델 그대로.
- **지연 생성.** 장에 들어와 수십 초 머문 뒤에야 생성한다. 목차를 훑어 넘기는 것만으로는 호출되지 않는다. 미리 만드는 범위는 현재 장과 다음 장까지만.
- **하루 상한.** 백그라운드 덱 생성 횟수의 일일 한도(기본 20회 안팎). 초과하면 조용히 멈추고 코치 탭에 표시한다.
- **한도 인식.** 구독 사용률이 일정 수준(예: 70%)을 넘으면 백그라운드 생성을 멈춘다. 사용자의 직접 질문이 항상 우선이다.
- **직렬화.** 동시 실행 1개. 사용자의 채팅이 스트리밍 중이면 대기한다.
- **긴 장 나누기.** 일정 분량(예: 6천 단어)을 넘으면 절 단위로 나누고, 읽고 있는 절부터 만든다.
- **투명성.** 설정 화면에 "오늘 코치가 쓴 호출 수"와 "캐시에서 해결한 횟수"를 보여 준다.

**로컬 모델에 대하여.** Ollama는 직전 릴리스에서 걷어냈으므로 코치를 위해 다시 들이는 것은 권하지 않는다. 대신 LLM이 아닌 로컬 계산을 적극적으로 쓴다. 카드 선별, 수준 추정, 막힘 감지, 캐시 조회는 모두 단순 산술이다. 코치 모델 설정은 기존과 같은 `provider:model` 문자열을 받게 해 두면, 나중에 로컬 제공자가 다시 생길 때 그대로 꽂을 수 있다.

**Wikipedia.** 인물, 사건, 지명 같은 고유명사 카드는 Wikipedia 요약 API로 LLM 없이 내용과 그림을 보강할 수 있다. 다만 읽고 있는 용어가 외부로 나가는 것이므로 설정에서 켜고 끌 수 있게 하고, 요청은 메인 프로세스에서 사용자 정보 없이 보낸다.

### 4.4 수준과 취향 추정

**기록하는 사건.**

| 사건 | 의미 | 신호의 세기 |
|---|---|---|
| 카드를 열어 봄 (호버 유지) | 약한 관심 | 약한 긍정 |
| "더 자세히" 누름 | 필요했음 | 강한 긍정 |
| 주석으로 저장 | 가치 있었음 | 가장 강한 긍정 |
| "이미 알아요" | 너무 쉬움 | 난이도 축에 대한 부정 (수준을 올림) |
| "이런 건 그만" | 종류가 안 맞음 | 종류 축에 대한 부정 |
| 그냥 닫음 | 모호함 | 약한 부정 |
| 표시됐지만 지나침 | 매우 모호함 | 거의 반영하지 않음 |
| 카드가 없던 구절을 선택해 Ask AI | 코치가 놓침 | 그 난이도의 문턱을 낮춤 |

거절을 두 버튼으로 나누는 것이 이 설계의 요점이다. 단순히 "닫음"만 세면 "쉬워서"인지 "관심 없어서"인지 "바빠서"인지 구분할 수 없고, 추정이 엉뚱한 방향으로 흘러간다. 마지막 줄의 "놓침" 신호도 중요하다. 지금의 질문 창 사용 기록이 그대로 코치의 학습 자료가 된다.

**모델.** 처음부터 복잡하게 가지 않는다.

- (분야 × 카드 종류 × 난이도 구간)별로 수락과 거절의 가중 횟수를 센다. 베타 분포의 두 숫자다.
- 카드를 보일지는 그 칸의 수락 확률 추정치가 문턱을 넘는지로 정한다. 가끔은 문턱 아래 카드도 일부러 하나씩 보여 준다(탐색). 그래야 한번 "전문가"로 굳어진 뒤에도 바로잡을 기회가 생긴다.
- 오래된 기록은 서서히 가중치를 줄인다. 사람은 책을 읽으며 성장한다.
- 수준은 **분야별**로 둔다. 덱 호출이 돌려주는 `domain` 태그를 쓴다. 한 분야의 전문가가 다른 분야에서는 초심자인 것이 보통이다.

**첫 만남 문제.** 기록이 없을 때는 세 가지를 쓴다. (1) 책을 처음 열 때 한 번 누르는 선택지 "이 분야가 처음 / 어느 정도 안다 / 전공이다". 건너뛸 수 있다. (2) `USER.md` 의 기존 프로필. 덱 생성 프롬프트에 요약을 넣어 "이 사용자가 이미 알 법한 것"을 LLM이 미리 표시하게 할 수 있다. (3) 그래도 없으면 중간 수준에서 시작한다.

**사용자가 볼 수 있고 고칠 수 있어야 한다.** 설정과 코치 탭에 "코치가 추정한 수준: 이 분야 중급"을 보여 주고 슬라이더로 직접 고치게 한다. 각 카드에는 "왜 보였는지"를 한 줄로 달 수 있다. 추정은 편의일 뿐이고, 사용자가 정한 값이 항상 우선한다. 사건 기록은 기기 안의 SQLite에만 남긴다.

**막힘 감지.** 문단 길이로 예상 읽기 시간을 계산하고(이미 분당 200단어 기준이 있다), 실제 체류가 그 몇 배를 넘거나 앞으로 되돌아가면 "막힘"으로 본다. 포커스 모드에서는 활성 문단이 정확히 잡히므로 신호가 가장 좋다. 막힘이 감지돼도 LLM을 부르지 않는다. 그 문단에 붙은 카드를 드러내거나 "풀어 드릴까요?" 칩을 띄울 뿐이고, 호출은 사용자가 누른 뒤에 일어난다.

### 4.5 얼마나 나설 것인가

방해가 되는 코치는 꺼지게 마련이므로, 사용자가 한 번에 조절할 수 있는 다이얼을 둔다.

| 단계 | 동작 |
|---|---|
| 끔 | 지금과 동일 |
| 조용히 (기본 권장) | 본문 밑줄과 호버 카드만. 먼저 말을 걸지 않음 |
| 제안 | 여백 칩, 막힘 감지 제안, 장 앞뒤 브리핑 추가 |
| 적극 | 확인 질문과 반론 카드까지 적극적으로 |

먼저 말을 거는 제안에는 규칙을 둔다. 문단 중간에는 끼어들지 않고 문단 끝이나 페이지 넘김 같은 경계에서만 나타난다. 일정 시간에 하나만 띄운다. 연속으로 몇 번 거절당하면 그 세션에서는 스스로 조용해진다. 포커스 모드에서는 여백 칩만 쓰고 팝업은 띄우지 않는다.

### 4.6 추가할 코드 구조

```
src/shared/coach.ts                  카드, 덱, 사건, 프로필 타입과 선별 함수(순수 함수)
src/main/coach-store.ts              coach.sqlite: decks, cards, events, profile, usage
src/main/coach-service.ts            작업 큐, 예산, 덱 생성 프롬프트, 닻 검증
src/main/wikipedia-service.ts        (선택) 요약 조회와 캐시
src/main/ipc-handlers.ts             coach:* 채널 추가 (ai:chat 과 분리된 AbortController)
src/preload/index.ts                 window.api.coach
src/renderer/src/store/useCoachStore.ts
src/renderer/src/components/DocumentReader/hooks/useCoachMarks.ts   Range 등록, 호버 판정
src/renderer/src/components/DocumentReader/hooks/useReadingSignals.ts  체류, 되돌아감
src/renderer/src/components/DocumentReader/CoachCard.tsx            LinkTooltip 확장
src/renderer/src/components/DocumentReader/CoachRail.tsx            여백 칩
src/renderer/src/components/ChatPanel/CoachTab.tsx
src/renderer/src/components/SettingsModal.tsx                       코치 설정 구역
```

기존 흐름과의 연결은 세 군데다. "더 자세히"는 `sendMessage({ quotedText })` 를 그대로 부르되 추정 수준을 한 줄 덧붙인다. "주석으로 저장"은 기존 주석 저장 경로를 쓴다. `TextSelectionMenu` 의 Ask AI는 "놓침" 사건을 기록한다.

선별 로직을 `shared/` 의 순수 함수로 두면 기존 `tests/*.test.mjs` 방식으로 단위 테스트할 수 있고, 덱 생성은 기존 구독 모의 서버(`tests/fixtures`, `tests/helpers/subscription-mock.ts`)로 검증할 수 있다.

## 5. 단계별 구현

각 단계는 그 자체로 쓸 수 있는 상태에서 끝나도록 나눴다.

### 0단계: 검증 (작게, 먼저)

- `sample/DPRH.md` 와 EPUB 한 장으로 덱 생성 프롬프트를 실제로 돌려 본다. 지연 시간, 구독 사용률 변화, 카드 품질, 닻 검증 통과율을 잰다. 저렴한 모델과 기본 모델을 비교한다.
- CSS Custom Highlight API가 Markdown 뷰와 epub.js iframe 양쪽에서 동작하는지, 기존 하이라이트와 검색 표시와 겹쳐도 괜찮은지 확인한다.
- 통과 기준: 덱 하나가 감당할 만한 시간과 사용률 안에 만들어지고, 카드의 대부분이 닻 검증을 통과할 것. 미달이면 4.1의 스키마와 분할 크기를 조정한다.

### 1단계: 조용한 코치 (첫 출시 범위)

- 덱 생성, 캐시, 작업 큐, 하루 상한.
- 본문 밑줄과 호버 카드. 카드의 네 버튼(더 자세히, 주석으로 저장, 이미 알아요, 이런 건 그만).
- 사건 기록은 시작하되 아직 추정에는 쓰지 않는다. 수준은 설정의 수동 선택(처음, 중간, 전공) 하나로만 거른다.
- Markdown과 EPUB 모두. 0단계에서 EPUB 쪽이 어렵다고 나오면 Markdown 먼저.

### 2단계: 배우는 코치

- 사건 기록으로 분야별 수준과 종류별 취향을 추정하고 선별에 반영한다.
- Ask AI의 "놓침" 신호 연결.
- 추정 수준 표시와 수동 조정, "왜 보였는지".

### 3단계: 먼저 말 거는 코치

- 여백 칩, 막힘 감지, 장 앞 브리핑과 장 뒤 정리, 확인 질문.
- 나서는 정도 다이얼과 빈도 제한.
- 채팅 패널의 코치 탭.

### 4단계: 덜 쓰고 더 주기

- Wikipedia 요약 보강.
- 책을 넘나드는 용어 캐시(다른 책에서 만든 같은 용어 카드 재사용).
- 내 주석과 예전 질문 답변을 카드로 끌어오기.
- 사용량 표시, 구독 한도 연동 일시 정지.

### 5단계: 기억과 연결

- 코치 프로필 요약을 `USER.md` 와 Hindsight에 반영해 채팅 답변의 눈높이도 함께 맞춘다.
- "연결자" 카드를 Hindsight 회상으로 실제 내 독서 이력과 잇는다.
- 확인 질문의 간격 복습, 카드를 주석 포함 EPUB 내보내기에 싣기.

## 6. 위험과 대응

| 위험 | 대응 |
|---|---|
| 카드 내용이 틀림 | 설명은 두 문장 이내로 짧게, "이 책의 맥락에서"로 한정. AI가 만든 것임을 표시. Wikipedia 출처 병기. 깊은 설명에서는 기존 웹 검색 옵션 사용 가능 |
| 위치가 어긋남 | 닻 문자열 검증. 못 찾으면 버림 |
| 방해가 됨 | 기본값은 "조용히". 표시 상한, 빈도 제한, 연속 거절 시 침묵 |
| 구독 한도를 갉아먹음 | 장당 1회, 하루 상한, 사용률 기준 정지, 사용자 질문 우선, 사용량 공개 |
| 추정이 한쪽으로 굳음 | 거절 사유 분리, 탐색용 카드, 시간에 따른 감쇠, 수동 조정 우선 |
| 백그라운드 작업이 채팅을 끊음 | 별도 IPC, 별도 중단 제어, 직렬 큐 |

## 7. 정해 주셔야 할 것

구현에 들어가기 전에 아래 네 가지만 정하면 된다. 괄호 안은 권장안이다.

1. 코치 전용 모델의 기본값 (저렴한 모델로 시작하고 0단계 실측 뒤 확정)
2. Wikipedia 보강을 넣을지 (4단계에서, 기본은 꺼 둠)
3. 첫 출시 범위를 Markdown과 EPUB 동시로 할지 (0단계 결과에 따름. 가능하면 동시)
4. 나서는 정도의 기본값 ("조용히")
